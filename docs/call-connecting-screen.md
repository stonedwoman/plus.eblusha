# Экран установления звонка — спецификация для нативных клиентов (Android / iOS)

Эталон — веб-реализация в этом же репозитории, выкачена 2026-09-30 и проверена двумя кругами адверсариального ревью. Её файлы (ТОЛЬКО ЧТЕНИЕ):
- `frontend/src/ui/components/callConnectView.ts` — модель: сигналы → этапы/узлы/связи/факты/заголовок/готовность; темп показа (`usePacedConnectSignals`, `applyPacing`); `withPeerSync`. **Переносить логику один в один.**
- `frontend/src/ui/components/CallOverlay.tsx`, функция `ConnectProgressWatcher` (ищите по имени; ~250 строк) — какие реальные события дают каждый сигнал, рукопожатие, готовность собеседника, таймауты, статистика маршрута. Остальное в этом файле читать не нужно.
- `frontend/src/ui/components/CallConnecting.tsx` + `callConnecting.css` — внешний вид (дизайн «вариант 2»).

## Внешний вид (дизайн 2)
Тёмная панель с мягко скруглёнными углами (сине-графитовая палитра, НЕ оранжевая: фон #0D1722, поверхность #14202E, граница #293A50, текст #EEF3FF, приглушённый #AABCD5, синий акцент #4B7BFF, бирюзовый #64DDAA для готового, фиолетовый #8758FF для сервера, красно-розовый #FF5C7A для ошибки). Сверху — компактная карточка фактов (до трёх строк с иконками: «Сквозное шифрование», «Через ретранслятор Cloudflare»/«Через наш ретранслятор»/«Прямой путь», «45 мс до сервера»). По центру — заголовок текущего действия и пояснение. Ниже — горизонтальная цепочка круглых узлов с кольцом цвета роли: **Вы** (мятный, иконка человека) → **ретранслятор** (синий, облако; появляется ТОЛЬКО когда путь через него подтверждён) → **Сервер Еблуши** (фиолетовый, иконка сервера; под ним задержка «45 мс») → **собеседник** (мятный, настоящий аватар/инициалы; в группе — название и «N участников»). Между узлами линии: пунктир «ждёт», бегущий пунктир «прокладывается», сплошной градиент с бегущей светящейся точкой «проложен» (точка едет ТОЛЬКО по проложенным участкам). За цепочкой — 2–3 медленные полупрозрачные волны (цикл 10–19 с, сине-бирюзовые слева, сине-фиолетовые справа). Под цепочкой — карточки этапов в ряд (телефон: сетка 2 колонки): номер/галочка + подпись; состояния done (бирюзовый кружок с галочкой), active (синяя рамка и подсветка, бегущая дуга вокруг номера), waiting (приглушено). Внизу — капсула «Отменить» (всегда доступна). Узел «ждёт» — приглушённое кольцо, «подключается» — пульсирующий ореол отдельным слоем + бегущая дуга, «готов» — спокойное насыщенное кольцо. «Меньше движения» (Android: Settings.Global.ANIMATOR_DURATION_SCALE == 0 / iOS: accessibilityReduceMotion) — без волн, точек и пульсаций. Ошибка — та же панель: иконка щита в красном кольце, заголовок, текст, кнопка «Закрыть».

## Этапы (стабильные идентификаторы, порядок показа)
1. `signaling` «Договариваемся о звонке» — сервер выдал LiveKit-токен.
2. `crypto-prepare` «Готовим шифрование» — ТОЛЬКО 1:1: ключ разговора получен, комната создана с E2EE-опциями.
3. `route` «Ищем путь к серверу» — Room подключён (RoomEvent.Connected / .connected).
4. `crypto-enable` «Включаем шифрование» — ТОЛЬКО 1:1: шифрование реально включено на нашем соединении (Android: E2EE-состояние локальной дорожки OK / если SDK не даёт отдельного события — момент публикации локальной дорожки в E2EE-комнате; НЕ выдумывать: если подтверждения нет, этап остаётся активным).
5. `publish` «Передаём ваш голос» — микрофон опубликован; при выключенном микрофоне заголовок «Микрофон выключен» и этап сразу сделан; при отказе микрофона — «Микрофон недоступен», сделан, продолжаем без микрофона.
6. `wait-peer` «Ждём собеседника» (группа: «Подключаем участников») — см. готовность собеседника. Гейт этапа — все локальные ступени сделаны.
Групповой звонок: этапов 2 и 4 нет, нумерация сплошная 1–4; плашки «Сквозное шифрование» в группе нет никогда.

Заголовки по активному этапу: «Подключаем звонок… / Договариваемся о соединении», «Готовим защиту… / Подготавливаем сквозное шифрование», «Прокладываем путь… / Ищем соединение с сервером Еблуши», «Меняем маршрут… / Пробуем соединиться с сервером напрямую» (только если в клиенте есть такой откат), «Включаем шифрование… / Проверяем защищённое соединение», «Подключаем микрофон… / Готовим передачу вашего голоса», «Ждём собеседника… / Собеседник ещё не в комнате звонка», «Собеседник подключается… / Ждём звук и подтверждение шифрования с той стороны», «Синхронизируемся… / Собеседник вот-вот подключится», группа: «Подключаем участников… / Ждём звук от участников разговора»; готово: «Соединение установлено / Начинаем разговор».

## Честность (главный принцип)
Ничего не завершается по таймеру, нет процентов и «осталось N секунд», ретранслятор не показывается до подтверждения, «Сквозное шифрование» — только когда реально включено, задержка — только из реального измерения (нет измерения — строка скрыта), собеседник «готов» — только по реальным признакам. Ни одно реальное действие (подключение, публикация, приём) НЕ задерживается ради показа.

## Темп показа (usePacedConnectSignals)
Реальные ступени показываются по очереди: ступень k показывается сделанной не раньше, чем (а) она сделана на самом деле, (б) все предыдущие показаны, (в) с предыдущего показа прошло dwell = max(400 мс, 3000 / (N + 1)), где N — число ступеней этого звонка (см. `milestoneFlags`: signaling, [keys], connected, [e2ee], [publish — если микрофон не выключен/не недоступен], peer — для 1:1 всегда; для группы — «кто-то слышен», если в комнате есть люди, иначе «подключились»). Заключительная пауза «Соединение установлено» — тоже одна ступень (отсюда +1). Часы монотонные. Откат реальности (обрыв до готовности) отражается сразу. Если подключение само идёт дольше — темп не вмешивается. Экран уходит, когда `settled` (все ступени + пауза) и собеседник «готов» с учётом рукопожатия (`withPeerSync`), затем ~220 мс растворения; разговор под ним уже идёт.

## Рукопожатие (синхронное открытие у обоих) — обязательно совместимо с вебом
Data-канал LiveKit, **reliable**, topic `eb.connect`, payload JSON `{"v":1,"state":"connecting"|"settled","audio":true|false}` (audio — будем ли передавать звук: микрофон не выключен и доступен).
- «connecting» шлём при RoomEvent.Connected и при ParticipantConnected (широковещательно); «settled» — когда локальная картина дорисована (paced settled). «settled» отправляем даже в переподключении (не гейтить на Connected), «connecting» — только из Connected.
- На чужое «connecting» отвечаем своим текущим состоянием ОДИН РАЗ на identity (адресно, destinationIdentities=[identity]); повторное «connecting» не сдвигает `since` (помним первое). При уходе всех собеседников — сброс.
- Только для 1:1 (в группах рукопожатия нет, peerSettled=true).
- peerSettled: пришло «settled» → true; «connecting» → через 8 с после первого «connecting»; ничего не приходило (телефон-старый клиент, веб) → собеседник «готов» И наше «connecting» реально отправлено, и с max(момент готовности, момент отправки) прошло 1,5 с.
- Пока собеседник «готов», но не peerSettled — показываем presence `settling` («Синхронизируемся…»), узел активен, участок «прокладывается».

## Готовность собеседника (presence)
- в комнате никого → `absent`;
- есть подписанная аудиодорожка и (1:1 E2EE) шифрование подтверждено → `ready` («heard»);
- дорожка подписана, но E2EE не подтверждено → `joining` без срока; через 15 с — ошибка «Собеседник не подтвердил сквозное шифрование. Продолжить без шифрования нельзя.»;
- аудиодорожка объявлена, но не подписана → `joining` без срока;
- собеседник сообщил audio:false → `ready`; прислал «settled» → `ready`; прислал «connecting» → `ready` через 8 с; ничего не слал → `ready` через 5 с после появления.
Группа: готовы, когда наша часть готова и (в комнате никого — известно только ПОСЛЕ подключения — или хоть кто-то слышен).

## Маршрут и задержка
Через ретранслятор/напрямую и RTT — из WebRTC-статистики ВЫБРАННОЙ пары кандидатов (transport.selectedCandidatePairId, иначе nominated/succeeded); relay, если хоть один кандидат пары — relay; имя ретранслятора из url нашего relay-кандидата (cloudflare → «Cloudflare», eblusha → «Наш ретранслятор», иначе host). Опрос раз в секунду, пока экран виден. Если SDK платформы не отдаёт такую статистику — узла ретранслятора и фактов о пути НЕТ (цепочка из трёх узлов), это допустимо; выдумывать нельзя.

## Ошибки
Не получили токен / комната не подключилась → «Не удалось подключиться» + текст + «Закрыть» (существующий путь завершения). Ошибка E2EE — существующий текст под заголовком «Защищённый звонок недоступен». Отказ микрофона — НЕ ошибка: входим без микрофона. Отмена — всегда, вызывает существующий hangUp/endCall, повторные нажатия не дублируют.

## Где показывать
Поверх интерфейса разговора с момента, как звонок стал активным для нас, до готовности (защёлка: назад не возвращается до конца звонка). Существующий экран дозвона «Звоним…» (исходящий, до принятия) остаётся как есть; входящий экран принять/отклонить — как есть. Если на платформе комната подключается ещё на дозвоне (Android так делает) — это нормально: после принятия экран покажет уже сделанные ступени в темпе и дождётся собеседника. Для группы экран уходит, как только наша часть готова (и никого нет) — не ждать всех приглашённых.

## Ограничения
- Не переписывать сигналинг, E2EE, выбор маршрута, существующие пути завершения; никакой параллельной машины состояний, управляющей звонком.
- Не устанавливать новых зависимостей; стек и соглашения проекта (Compose/Material3 у Android, SwiftUI у iOS); комментарии в стиле проекта (русские, объясняют «почему»).
- Никаких настоящих звонков, никакой установки на телефон, никакого релиза. Только сборка.


## Дозвон в том же оверлее (добавлено 2026-09-30; на вебе и Android уже сделано)
Экран подключения появляется **в момент набора**, а не после ответа — один оверлей вместо «Звоним…» + экрана подключения. Эталон: `callConnectView.ts` (сигналы `ringing?: boolean` — true ждём ответа / false ответил / undefined дозвона не было — и `ringingSeconds`; ступень `ring`; состояние узла `ringing`), `CallConnecting.tsx` + `callConnecting.css` (кольца `.eb-cn__ring`, `--eb-ring-period`, `--eb-ring-offset`), `CallOverlay.tsx` (проп `dialing`, `onCancelDial`).
1. Пока не ответил: первая карточка «Ждём ответа» активна (единственная активная), заголовок «Звоним…», подзаголовок «Ждём ответа собеседника · m:ss» (таймер раз в секунду), узел собеседника — цветной аватар и три расходящихся кольца со сдвигом 0 / 0,13 / 0,30 периода; период 2 с (если есть свой гудок — его период и фаза). Участки — пунктир «ждёт», сервер — «ждёт». «Отменить» = существующий сброс вызова.
2. После ответа: карточка «Ждём ответа» → ✓, заголовок «Собеседник ответил» (подзаголовок «Договариваемся о соединении»; если локальная часть уже готова, а собеседника нет в комнате — «Входит в комнату звонка»), дальше обычные этапы в темпе. Ступень «ответ» — ПЕРВАЯ веха темпа (`milestoneFlags`), поэтому каскад этапов идёт после ответа, даже если комната подключилась на дозвоне.
3. Локальные этапы гейтить на `!ringing` (и на вебе, и на Android так), независимо от того, когда подключается комната. Группы дозвона не имеют — там как раньше. Отклонение/таймаут — существующие пути, экран просто уходит.
