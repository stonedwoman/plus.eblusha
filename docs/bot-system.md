# Бот «Еблуша» — часть системы: контракт сервера для клиентов (v1)

Решения владельца 2026-10-10. Сервер: `src/lib/systemBot.ts`, `src/routes/bot.ts`, `src/lib/botContract.ts`.
Сервис бота: `bot/` (`bot/README.md`). Клиенты: веб, ПК-натив (главный), Android, iOS — все четыре.

Коротко: бот не участник бесед. Он отвечает в любой обычной беседе, если к нему обратились, — от
системного пользователя (`isBot`), которого НЕТ в `participants`. Клиент должен уметь показать
сообщение, «печатает…» и реакцию от НЕучастника, подсветить режим «Спросить», показать кнопку
«Уточнить» и настройку «Чат с Еблушей».

Разговор с ботом не требует цитирования, и бот помнит свои разговоры (решения владельца 2026-10-10 и
2026-10-11, п. 8): в «Чате с Еблушей» — весь чат, в обычной беседе обращение «Еблуша, …» по-прежнему
обязательно, но бот помнит ВСЕ свои разговоры в ней — обращения к нему от любого участника и свои ответы
(«Еблуша, а в Мельбурне?» после вопроса про Сидней, «что я спрашивал вчера?»); остальную переписку людей не
видит. Клиентам для этого ничего делать не надо — историю бот берёт у сервера сам.

## 1. Как узнать бота

Верить только серверным полям `isBot` (столбцы БД). `metadata.bot` / `metadata.isBot` — подсказки, их
задаёт сервер, а из сообщений людей он такие ключи вырезает.

| Где | Поле |
|---|---|
| любое сообщение (ответ `/conversations/send`, `GET /conversations/:id/messages`, `message:new`, `message:notify`, `message:update`) | `message.isBot: boolean` (верхний уровень) и `message.sender.isBot` |
| цитата ответа | `message.replyTo.isBot` |
| реакции | `message.reactions[].user.isBot` |
| список бесед `GET /api/conversations` | `conversation.isBotChat` (это «Чат с Еблушей»), `conversation.participants[].user.isBot` (бот бывает участником только там), `conversation.messages[0].sender.isBot` (последнее сообщение) |
| карточка `GET /api/users/:id` | `user.isBot` |
| себя `GET /api/status/me` | `user.isBot` (у людей `false`) |

### Профиль бота: `GET /api/bot`

```json
{
  "bot": { "id": "cmv2d0qso0000jb5odhg6121n", "displayName": "Еблуша", "avatarUrl": "/api/files/….eblusha",
           "eblid": "7087", "bio": "Бот мессенджера. …", "isBot": true },
  "botChat": { "botChatEnabled": false, "conversationId": null },
  "secretChatRefusal": "Еблуша не работает в секретных чатах: их сообщения не видит даже сервер, и боту они не уходят."
}
```

`404 {code:"BOT_NOT_CONFIGURED"}` — бота нет: всё «ботовое» в интерфейсе спрятать. Запрос доступен любому
вошедшему пользователю; id бота стабилен — можно кэшировать на сессию.

## 2. Сообщение бота (решение 2)

- Отправитель — НЕ участник беседы: имя брать из `message.sender.displayName` («Еблуша»), а не из списка
  участников; аватар — фирменная «Б» (оранжевая; `bot.avatarUrl` — запасной вариант).
- Вид: оранжевая полоса слева, «Б», подпись «бот» у имени.
- `metadata.bot = { v: 1, kind, triggerMessageId?, askerId? }`, где `kind`:
  `answer` (ответ модели), `command` (ответ команды, отчёт о выполненной просьбе), `notice` (служебное:
  лимит, «не понял», уведомление владельцу), `confirm` (вопрос «да/нет»: план изменений сервера Valheim
  или старый вопрос владельцу), `welcome` (приветствие в «Чате с Еблушей»).
  `triggerMessageId` — на какое обращение ответ (обычно совпадает с `replyToId`). `askerId` — кто спросил
  (автор обращения, по разрешению которого бот написал; у отчёта агента Valheim — подтвердивший «да»);
  у уведомлений без обращения и у старых ответов его нет.
- **Удаление ответа бота** (`POST /api/messages/delete {messageId}`, для всех, как своё сообщение): ответ бота
  может удалить тот, кто спросил, а в «Чате с Еблушей» — его владелец (любое сообщение бота, в т. ч.
  приветствие). Пункт «Удалить» показывать по тому же правилу: `isBot` и (беседа — «Чат с Еблушей» или
  `metadata.bot.askerId` = я; нет `askerId` — автор обращения `triggerMessageId` = я). Сервер решает сам:
  не участнику беседы, не тому, кто спрашивал, и в секретных беседах — `403`; повторное удаление уже
  удалённого ответа участником — `200`. Остальным сообщения бота не удаляются.
- Кнопка **«Уточнить»** под ответом бота `answer`/`command` (в группах и личках; в «Чате с Еблушей» —
  по желанию): начинает ответ (reply) с включённым режимом «Спросить» и фокусом в поле ввода. Ответ на одно
  обращение бывает несколькими сообщениями подряд (длинный текст частями, картинки отдельно; у всех один
  `metadata.bot.triggerMessageId`, а `replyToId` — только у первой части). Одинаково во всех клиентах:
  кнопка ОДНА — под последней частью, а ответ ставится на ПЕРВУЮ часть (она цитирует вопрос). Сервер и сам
  отдаёт боту весь ответ и вопрос, на какую бы часть человек ни ответил (п. 7).
- `confirm` — вопрос «да/нет». Чаще всего это **план агента Valheim** («Ответьте «да», чтобы применить,
  или «нет».»): приходит в ЛЮБОЙ беседе, где просили, и ответить может ЛЮБОЙ её участник (решает бот:
  подтверждают только привязанные игроки, остальным он сам вежливо откажет — клиенту ничего проверять
  не нужно). Реже — старый вопрос владельцу в его «Чате с Еблушей». Можно показать быстрые «Да» / «Нет» —
  они шлют ответом (reply) на это сообщение текст «да» / «нет». Когда на этот вопрос уже есть МОЙ ответ —
  кнопки прятать (ответ другого человека их не прячет: бот сам скажет, что план уже подтвердили).
- Ответ на план и отчёт бот шлёт ОТДЕЛЬНЫМИ сообщениями позже (через минуты или часы — сервер может
  ждать, пока все выйдут из игры): `command` ответом на «да» того, кто подтвердил.
- **Карточка карты** (Valheim): картинка бота, у вложения `metadata.link` (только `https://`) — нажатие
  открывает эту ссылку (живую карту) вместо просмотрщика. Старые карточки без `link` узнаются по имени
  вложения `karta-*.png` и ведут на `https://v.koban.uk/map/`. Адрес из текста ответа не угадывать.
- Разметка — безопасное подмножество (как у обычных сообщений), картинки — отдельным сообщением IMAGE
  с `width/height` во вложении.
- Квитанции, непрочитанные, превью в списке, пуши — как у обычного сообщения. Пуш: `senderName: "Еблуша"`,
  `senderId` = id бота, без текста.
- Цитата ответа на сообщение бота (`replyTo.isBot`): автор «Еблуша».
- Реакция бота (👍 на «спасибо») — обычная реакция от `user.isBot` (имя «Еблуша»); клиент её показывает,
  хоть бот и не участник.

## 3. «Еблуша печатает…»

Событие то же, что у людей, в комнату беседы (клиент должен быть в ней — `conversation:join`):

```
conversation:typing_update { conversationId, userId: <id бота>, isTyping: true|false, displayName: "Еблуша", isBot: true }
```

Бот повторяет `isTyping:true` каждые ~3 с, пока думает; сервер сам шлёт `isTyping:false` через 10 с после
последнего. Показывать «Еблуша печатает…» по `isBot`/`displayName`, не ища бота среди участников.

## 4. Кому адресовано сообщение (режим «Спросить», решение 5)

Решает сервер; правила (сообщение не SYSTEM/CALL, беседа не секретная):

1. `metadata.botAsk === false` → НЕ боту (никогда);
2. беседа — «Чат с Еблушей» этого человека → боту (всегда); ВНЕ его голосовое (`type: "AUDIO"`) → НЕ боту,
   даже ответом боту и с `botAsk: true` (слушать бот не умеет, а «напиши текстом» в общей беседе — шум);
3. `metadata.botAsk === true` → боту (режим «Спросить»);
4. пересылка (`metadata.forwardFrom`) → не боту;
5. текст начинается с «Еблуша» и затем `,` `:` `!` (можно с пробелами и `@` впереди; регистр не важен,
   ё = е, в имени допустимы похожие латинские e a y b 6 w) → боту;
6. текст начинается с `/eb` или `/еб` (любой регистр), дальше пробел или конец → боту (молчаливый синоним
   обращения: понимать, но нигде людям не подсказывать — команд у бота нет, всё словами);
7. `replyToId` — сообщение бота в этой же беседе (`replyTo.isBot`) → боту.

Правка сообщения (`/messages/update`) бота не зовёт. Адресованное сообщение сервер сохраняет с
`metadata.botAsk: true` — по нему можно пометить вопрос «→ Еблуше» (по желанию). Правка «Еблуша, …» в текст
без обращения этот признак снимает (п. 8).

Что делает клиент:
- Плашка **«Спросить Еблушу»** (оранжевая) в поле ввода, когда текст начинается как в п. 5/6, когда
  отвечаешь на сообщение бота или нажал «Уточнить». Текст НЕ менять («Еблуша,» остаётся в сообщении).
- Плашка активна → слать `metadata: { …, botAsk: true }` (сервер и сам поймёт, но так надёжнее).
- **Backspace** в начале поля (курсор на 0, без выделения), когда плашка видна, — убрать плашку: сообщение
  уходит обычным, с `metadata: { …, botAsk: false }` (ответ боту без вопроса, «Еблуша, …» человеку).
- В «Чате с Еблушей» плашка не нужна (там всё — боту); можно мелкую подсказку «сообщения здесь — для Еблуши».
- **Секретный чат**: плашку не показывать; если человек начал «Еблуша,»/«/eb», показать ЛОКАЛЬНУЮ строку
  `secretChatRefusal` (никуда не отправляется; текст секретки сервер не видит и боту не передаёт).

## 5. Настройка «Чат с Еблушей» (решение 3; по умолчанию ВЫКЛЮЧЕНА)

```
GET /api/bot/settings                       → { botChatEnabled: boolean, conversationId: string | null }
PUT /api/bot/settings { botChatEnabled }    → то же (идемпотентно; 404 BOT_NOT_CONFIGURED; ≤ 20 в минуту)
сокет в user:<свой id>:  bot:settings { botChatEnabled, conversationId }
                        + conversations:new {conversationId} при включении / conversations:deleted при выключении
```

- Включение создаёт (или возвращает) беседу 1:1 пользователь↔бот: `isGroup:false`, `type:"CLOUD"`,
  участники — человек и бот. В первый раз бот здоровается (`metadata.bot.kind = "welcome"`).
- Выключение снимает участие человека (беседа пропадает из списка), история сохраняется и вернётся при
  повторном включении. «Покинуть беседу» в этом чате = выключить (без системной записи). Удаление беседы
  (`DELETE /conversations/:id`) стирает историю; следующее включение создаст новый чат.
- Узнать чат в списке: `conversation.isBotChat === true` (то же, что `!isGroup && participants.some(p => p.user.isBot)`;
  беседу из `conversations:new` клиент берёт из того же `GET /api/conversations`). Показ: название
  «Еблуша», «Б», вместо «в сети/был» — «бот»; без кнопок звонка (сервер всё равно сразу пришлёт
  `call:declined {conversationId, by:{id: <бот>}}`), без «секретного чата», «в контакты», местного времени.
- Команд нет: и здесь, и в остальных беседах — просто словами («как там сервер?», «перезапусти, когда все
  выйдут»). Здесь «да»/«нет» на план бота можно писать и без ответа (reply), если план — последнее его сообщение.
- В настройках: переключатель «Чат с Еблушей» и пояснение: «Личный чат с ботом: там можно писать без
  обращения, разговор он помнит. В остальных беседах зовите «Еблуша, …»».

## 6. Карточка бота и запреты сервера

`GET /api/users/:id` бота доступен всем (`isBot: true`). В карточке: «Еблуша», «Б», «бот», описание; без
«в контакты», «написать», «позвонить», «секретный чат». Можно кнопку «Открыть чат с Еблушей» (включает
настройку и открывает беседу).

Сервер отказывает (клиенту достаточно не предлагать эти действия):

| Запрос | Ответ |
|---|---|
| `POST /api/contacts/add` бота | 400 `BOT_NOT_CONTACT`; `/contacts/search` бота не находит |
| `POST /api/conversations` с ботом | 400 `BOT_NOT_PARTICIPANT` (группа) / `BOT_CHAT_VIA_SETTINGS` (1:1) |
| `POST /api/conversations/:id/participants` с ботом | 400 `BOT_NOT_PARTICIPANT` |
| `POST /api/threads/secret {peerUserId: бот}` | 403 `BOT_NO_SECRET` |
| `call:invite` в «Чат с Еблушей» | сразу `call:declined {by:{id: бот}}` |

Отправка сообщений людьми не изменилась; из `metadata` сервер вырезает служебные ключи `bot`, `isBot`,
а `botAsk` понимает как в п. 4.

## 7. Только для сервиса бота (клиенты не вызывают)

Обращение уходит боту задачей BullMQ `bot` (`src/lib/botContract.ts`: триггер, цепочка ответов,
разрешение). Бот отвечает учёткой с `isBot`:

```
POST /api/bot/messages { grant | userId, type: TEXT|IMAGE|FILE, content?, replyToId?, attachments?, kind?, linkPreview? }
POST /api/bot/typing   { grant, typing }
POST /api/bot/react    { grant, messageId, emoji }
POST /api/bot/followup { grant } → 201 { grant, expiresAt }
POST /api/bot/people   { grant, query?, ids? } → 200 { participants, matches, users, truncated }
POST /api/bot/history  { grant, after?, limit?, changesSince?, epoch? } → 200 { mode, messages, next, memory } (п. 8)
```

`grant` — только беседа обращения, ≤ 12 сообщений и 3 реакций, 20 минут; `userId` — уведомление в
«Чат с Еблушей» человека, если включён (иначе 409 `BOT_CHAT_DISABLED`). Человек удалил своё обращение,
пока бот думал, — ответ, реакция и «печатает» по этому `grant` получают 409 `BOT_TRIGGER_DELETED`.

`/followup` — **продолжение** для отчёта о долгой задаче (агент Valheim ждёт, пока все выйдут из игры, до
49 ч): новый `grant` на ту же беседу и то же обращение, 72 ч, ≤ 4 сообщений, без реакций. Брать только по
живому обычному `grant` (из продолжения — 400 `BOT_FOLLOWUP_NESTED`), не больше 2 с одного (429
`BOT_GRANT_EXHAUSTED`); обращение удалено — 409 `BOT_TRIGGER_DELETED` (и сообщения по продолжению — тоже).

Цепочка в задаче — предки обращения по `replyTo` в этой беседе (не больше 11). Встретив часть ответа
бота, сервер кладёт в цепочку ВСЕ части этого ответа (общий `triggerMessageId`) и идёт дальше вверх от
вопроса. Задачи, которые ждут бота дольше 30 минут (сервис бота лежал), сервер из очереди выбрасывает.

`/people` — люди для привязки персонажей владельцем (п. 9): участники беседы обращения (без бота), поиск
людей (не бот, не удалён, не заблокирован) по имени — подстрока или основа слова в падеже («Сане» → «Сан»),
по точному логину и по EBLID, имена по `ids` (≤ 20, без удалённых и заблокированных). Каждый человек —
`{ id, displayName, eblid, inConversation }`, в `matches` ещё `matchedBy: "name" | "username" | "eblid"`
(лучшие совпадения первыми, ≤ 25; `truncated` — подходящих могло быть больше); логин (`username`) не отдаётся
никогда. Сервер знает владельца (`BOT_OWNER_USER_ID` в `.env` backend) — только по обращению владельца (иначе
403 `BOT_OWNER_ONLY`) и среди всех людей; не знает — по любому обращению, но только среди людей, с которыми у
спрашивающего есть общая обычная беседа. Только по живому обычному `grant` (по продолжению — 400
`BOT_FOLLOWUP_NESTED`), ≤ 20 запросов на обращение (429 `BOT_GRANT_EXHAUSTED`), беседа удалена/секретная — 409
`BOT_CONVERSATION_GONE`. В журнал сервера — без текста запроса.

### Версия задачи: `v` и `rev`

`v` — несовместимая смена формы (бот отвергает задачу с чужим `v`), поэтому он остаётся `1`. Добавочные поля
идут ревизией `rev` (нет поля — ревизия 1): старый бот их не читает, новый бот без них работает по-старому.
Так старый бот с новым сервером и новый бот со старым сервером не ломаются (проверяют
`bot/test/unit/context.test.ts`, `bot/test/unit/memory.test.ts` с замороженным разбором rev 1 и
`test/bot-context.integration.test.ts`).

| rev | что добавлено |
|---|---|
| 1 | триггер `message`, цепочка `chain`, разрешение `grant` |
| 2 | `history` прямо в задаче — только в невыпущенной ветке, заменена ревизией 3 |
| 3 | истории в задаче нет; у сервера есть `POST /api/bot/history` — память бота (п. 8) |

## 8. Память бота о своих разговорах (`POST /api/bot/history`, rev 3)

Решения владельца 2026-10-10 («чтобы не обязательно было отвечать каждый раз») и 2026-10-11 («надо хранить
контекст всей переписки… компактировать, как в харнессах»): бот помнит ВСЕ свои разговоры в беседе — давнее
сводкой, свежее дословно (`bot/README.md`, «Память о своих разговорах»). Задача очереди истории не везёт; бот
берёт её сам, по разрешению задачи:

```
POST /api/bot/history { grant, after?: { at: ISO, id } | null, limit?: 0..500 (200), changesSince?: ms | null, epoch?: string | null }
→ 200 { mode: "botchat" | "recent", messages: BotHistoryMessage[], next: { at, id } | null,
        memory: { epoch, checkedAt, reset, changedFrom } }
```

- `botchat` — «Чат с Еблушей»: весь чат (обе стороны), без приветствия бота.
- `recent` — обычная беседа (личка двух людей, группа): ТОЛЬКО разговоры с ботом — обращения к нему от любого
  участника (`metadata.botAsk`, ставит только сервер) и его ответы (`isBot`), за всё время. Остальная переписка
  людей не читается вовсе.
- Везде: только беседа разрешения; без удалённых, истёкших, `SYSTEM`/`CALL`, зашифрованных и без ответов бота на
  обращение, которого больше нет (удалено, истекло, правкой перестало быть обращением). Порядок — `(createdAt,
  id)` по возрастанию после курсора `after`, не новее «сейчас» (что новее обращения, бот отсеивает сам). У ответа
  бота — `triggerId` (на какое обращение), у исчезающего сообщения — `expiresAt`. `next` — курсор следующей
  страницы; `limit: 0` — только `memory`.
- `memory` — журнал изменений беседы: удалили или поправили сообщение, которое бот мог запомнить (обращение,
  ответ бота, сообщение «Чата с Еблушей»; `POST /api/messages/delete`, `/update`), — сервер пишет это в Redis
  (`bot:memlog:<беседа>`, ≤ 500 записей, без срока). С `changesSince` (время сервера из прошлого ответа, бот
  хранит его) и `epoch` в ответе — `changedFrom`: самое раннее `createdAt` изменённого с тех пор (или null).
  `reset: true` — журнал ответить не может (сменился `epoch`, нужная часть вытеснена): бот собирает память с
  нуля. `checkedAt` берётся ДО чтения сообщений: изменение во время чтения попадёт в следующий ответ.
- Правка «Еблуша, …» в текст без обращения (имени или `/eb` в начале больше нет) снимает с сообщения
  `metadata.botAsk`: оно и ответ на него из памяти уходят. Ответ на сообщение бота, режим «Спросить» и «Чат с
  Еблушей» правкой не меняются.
- Только по живому обычному `grant` (по продолжению — 400 `BOT_FOLLOWUP_NESTED`), обращение удалено — 409
  `BOT_TRIGGER_DELETED`, беседа не та — 409 `BOT_CONVERSATION_GONE`, ≤ 200 страниц на обращение (429
  `BOT_GRANT_EXHAUSTED`). В журнал сервера — только числа (`bot: history`).

Клиентам для этого ничего делать не надо. Секретные беседы — как раньше: задач и разрешений оттуда нет.

## 9. Привязка персонажей к людям (сервис бота, инструмент модели)

Решение владельца 2026-10-10 (п. 13): ВЛАДЕЛЕЦ бота (`BOT_OWNER_USER_ID`) привязывает игровых персонажей к
людям свободной фразой в ЛЮБОЙ обычной беседе и в своём «Чате с Еблушей»: «Еблуша, Парасюха — это Саня»,
«Еблуша, РомаH — это я», «привяжи IiApaCiOxa к Сане», «отвяжи Парасюху». Остальные — только себя
(«мой ник в игре …», «РомаH — это я»); попытка привязать другого — вежливый отказ. Команд нет: смысл
понимает модель, проверки — в коде бота (`bot/src/core/links.ts`, инструмент `character_link`):
человек — сначала среди участников беседы, потом среди всех (`/api/bot/people`; не владельцу людей не ищем;
совпадение только по «основе» слова — «Сан» в «Оксана» — не человек, а повод переспросить); персонаж — по
списку известных серверу игры (похожие латинские буквы: IiApaCiOxa = Парасюха); неоднозначность — переспрос
с вариантами (в «Чате с Еблушей» — с EBLID, в обычной беседе у людей не из неё EBLID не показывается);
перепривязка — «Раньше этот персонаж был за «Саня»»; ответ — «Привязал: Саня — **IiApaCiOxa** (Парасюха).».
Задеть других (привязать, забрать, отвязать) — только по просьбе в самом обращении (персонаж или человек в его
тексте) или ответом на переспрос бота: просьба из памяти беседы не исполняется. Сервер знает владельца
(`BOT_OWNER_USER_ID` в `.env` backend) — `/api/bot/people` только по его обращениям (иначе 403
`BOT_OWNER_ONLY`) и среди всех людей; не знает — по любым, но только среди людей с общей беседой со
спрашивающим. Клиентам ничего делать не надо.
